What the download tests prove

The question each test answers is whether a web origin can read the bytes of a pCloud file at all. Only api.pcloud.com sends Access-Control-Allow-Origin: *; the content hosts it hands out do not.

  • getfilelink download fetches the file from a content host. Expected to fail from a web origin. This is why pCloud support is currently confined to the browser extension, where host_permissions bypass CORS.
  • file_pread download would read bytes from api.pcloud.com through the descriptor API. Expected to fail: file_open answers 2003 Access denied even with no credentials at all, so the descriptor API is closed to API clients.
  • getzip download asks api.pcloud.com for a single-member archive and extracts it in the browser. This is the remaining candidate. If it passes from a deployed origin, a plain web app or PWA can read pCloud files with no extension.

Can a web origin write a file back?

Reading was the question that forced pCloud support into the extension, but writing was never tested from a web origin, and Podium's current upload cannot work there. PCloudSrc.putFileSrc sends PUT with Content-Type: application/octet-stream, which is not a CORS-safelisted value, so the request is preflighted — and api.pcloud.com answers OPTIONS with Access-Control-Allow-Origin and Access-Control-Allow-Methods but no Access-Control-Allow-Headers.

multipart/form-data is one of the three safelisted Content-Type values, so a POST built from a FormData is a simple request and is never preflighted. This test runs both, then reads the file back with getzip and compares every byte: a write that returns result 0 is worthless to a score annotator if the annotations do not survive the trip.

The test works in its own folder, /podium-write-probe, uploads one file of random bytes, and deletes what it created. If the folder already existed it is left in place and only this run's uploads are removed. Re-enter the email and password first: the password is never kept between tests.

A few tens of kilobytes answer the CORS question but measure nothing, because the whole request is round-trip latency. Saving an annotated score uploads megabytes, so run the deployed-origin test at a realistic size as well.

The same run then exercises the five metadata methods Podium calls that no probe had reached: createfolder, listfolder on a subfolder rather than the root, renamefolder, renamefile, deletefile and deletefolder. They are plain JSON GETs like the proven listfolder, so they are expected to pass — but "expected to pass" is what was said about writing.

Is one digest reusable?

PCloudDirectAuth signs every request with a fresh digest, so every operation costs two round trips. getdigest returns an expiry, which implies a digest may be reused until then, but nothing has tested that pCloud actually accepts the same digest twice. This runs the same three listfolder calls both ways and reports the expiry window, so the implementation can cache the digest with a margin rather than guess.
